# Validation guidance

Run `npm ci` and `npm test` from this repository. The installation test uses a temporary Git repository and the published `skills` CLI to install the package into Claude Code, Codex, Cursor, and OpenCode project fixtures. It compares the installed runtime files with the source, including the validator and review references. No remote is contacted by that fixture.

Run `node skills/requirements/scripts/requirements.mjs validate <target-project>` to check a target project's canonical documents. Run `node skills/requirements/scripts/requirements.mjs apply <target-project> <candidate-directory>` to validate and apply a prepared candidate. See [integrity rules](../skills/requirements/references/integrity.md) for the document schema and historical invariant.

Deterministic checks can verify structure, IDs, references, hashes, and Git-visible paired updates. They cannot establish that user value or observed behavior is accurately described. Use the [human review checklist](../skills/requirements/references/review.md).

## Isolated scenario evaluation (2026-09-25)

A reviewer used disposable fixture projects outside this repository and inspected the skill instructions for first-use discovery, new-product elicitation, drift, conflicting evidence, and missing Git. The existing-project fixture included source, tests, package configuration, and a Git repository. A candidate with an overview, journey, quality constraint, evidence, one baseline ledger entry, and integrity metadata passed `stamp`, `apply`, and `validate`; validation reported uncommitted output separately and passed cleanly after commit. A new-product candidate with a parent/save/retry journey stamped successfully. `apply` to a project without Git failed with a draft warning, retained the candidate, and left canonical documents absent. An altered but unstamped conflicting candidate failed the hash check and left canonical files intact. Changing source behavior without updating documents did not change canonical requirements; the skill instructs the agent to investigate this drift and ask for confirmation.

These were scripted fixture simulations plus instruction review, not a live agent skill invocation. They verify the packaged file and CLI seams but do not verify the quality of an agent's questions, semantic judgment, or prose in an actual user conversation. Run live agent scenarios before claiming those aspects are proven.

## Agent skill exercise (2026-09-25)

A separate agent loaded the packaged skill instructions and worked in disposable fixture projects. In a book-search Git project it inspected UI, source, tests, README, and package configuration; the fixture's own tests passed 2/2. Given explicitly confirmed user behavior, it produced a concise overview, a search journey with visible availability and no-match recovery, evidence, an unresolved response-time measure, and exactly one baseline ledger entry. It recorded that opening details was absent from the inspected UI instead of changing the confirmed requirement. `stamp`, `apply`, and `validate` passed; validation warned about uncommitted output and passed cleanly after a commit in the disposable fixture.

For a new product, the agent produced a parent drawing-save journey with network-failure retry, then kept it as a stamped draft outside a project without Git. Validation reported missing Git and left canonical documents absent. This exercise used preconfirmed behavior, so it tested artifact production and draft handling, not the quality of interactive questioning. No package repository commit was made.

An additional interactive new-product run started with only “a small app to help my family keep our kids’ drawings.” The agent asked, in order, who uses it and why; how capture and successful saving appear; how a parent later finds a drawing; what happens after save failure; first-version priority and scope; and whether reliability or speed targets were known. The answers established an in-app photo, title, save confirmation, family collection browsing, retained photo/title and retry after failure, and unresolved numeric measures. The agent presented one proposed journey, two unresolved quality constraints, three interview evidence records, and one baseline ledger entry; it waited for explicit confirmation before `stamp` and `apply`. Post-apply `validate` passed with the expected uncommitted warning, and the canonical tree matched the candidate byte for byte. This run exercised elicitation and confirmation in a disposable Git fixture; it still does not prove how the skill will behave for every user or project.
