# Requirements document format and integrity commands

Run these commands with Node.js 18 or newer. The script is packaged with this skill.

```sh
node skills/requirements/scripts/requirements.mjs stamp <candidate-dir> <LED-revision>
node skills/requirements/scripts/requirements.mjs apply <target-project> <candidate-dir>
node skills/requirements/scripts/requirements.mjs validate <target-project>
```

`candidate-dir` is a complete proposed `docs/requirements` tree, with `README.md` directly inside it. `stamp` writes `integrity.json` from the candidate's actual file bytes. Run it after all prose changes and pass the ID of the newest ledger entry. `apply` validates the candidate before replacing the canonical directory. An invalid candidate remains at its original path and the canonical set stays intact. The caller chooses when to commit. `validate` checks the current files and available committed history. Without Git it returns an error; keep the documents as a draft. When requirements have uncommitted changes, it prints a separate warning because only committed history can be checked.

## Required files

- `README.md`: a `#` heading, nonempty `User groups:` and `Goals:` lines, and Markdown links to every journey. Links may be relative to the README as `journeys/slug.md`, or use `slug.md`.
- `journeys/<slug>.md`: `# REQ-001: Title`, then nonempty `Actor:`, `Goal:`, `User value:`, `Entry point:`, `Success:`, and `Failure and recovery:` lines. `Actions and responses:` has at least one numbered `1. User action -> Visible response` line. Slugs use lowercase letters, numbers, and hyphens.
- `non-functional.md`: a `#` heading and zero or more `- NFR-001: measurable condition or explicitly unresolved measure` lines. Leave the set empty when no quality constraint has been confirmed.
- `evidence.md`: at least one row such as `- EVD-001 | Source: interview | Provenance: participant group | Accessed: 2026-09-25 | Finding: search matters | Confidence: confirmed | Supports: REQ-001`. `Accessed` is optional where irrelevant; all other fields are required. Supported IDs must exist in the current journeys or quality constraints.
- `ledger.md`: `## YYYY-MM-DD` groups in strictly newest first order, with rows such as `- LED-001 | Decision: establish baseline | Reason: initial inspection | Affects: REQ-001, NFR-001 | Before: no maintained requirements | After: baseline requirements`. Each accepted change gets one entry. An existing ID's row must remain unchanged after commit.
- `integrity.json`: generated by `stamp`, with this structure:

```json
{
  "version": 1,
  "revision": "LED-001",
  "hashes": {
    "README.md": "64 lowercase hexadecimal SHA-256 digits",
    "journeys/find-book.md": "64 lowercase hexadecimal SHA-256 digits",
    "non-functional.md": "64 lowercase hexadecimal SHA-256 digits",
    "evidence.md": "64 lowercase hexadecimal SHA-256 digits",
    "ledger.md": "64 lowercase hexadecimal SHA-256 digits"
  }
}
```

The hash map contains every file in the set except `integrity.json`, and no extra paths. The revision equals the first ledger entry in the newest date group. Hashes detect local edits; they do not establish provenance.

## Committed history rule

For each Git commit that touches `docs/requirements`, including merge commits compared with each parent, the validator checks these conditions:

1. A change to any current document (`README.md`, a journey, `non-functional.md`, or `evidence.md`) includes changes to both `ledger.md` and `integrity.json` in the same commit.
2. A change to either `ledger.md` or `integrity.json` includes the other in the same commit.
3. Each revision after the baseline adds at least one ledger entry. Previously committed ledger entry rows remain byte-for-byte the same after trimming outer whitespace. New entries may be inserted in an existing date group.
4. A newly committed ledger entry may cite an ID present in its current documents or in an ancestor commit’s documents. The current working set and apply candidate use the same current-or-committed rule for the latest entry. This permits a removal while rejecting IDs that never existed in committed documents.
5. A committed integrity revision names the first ledger entry in that commit.

This rule detects exposed rewrites and unpaired commits in local Git history. It cannot verify the semantic accuracy of prose, uncommitted history, or history that Git no longer contains after force rewriting.
